# Manual database checkpoint

Google sign-in identifies a user. This migration prepares the tables and private
photo bucket that will hold that user's wardrobe. The React app still uses local
IndexedDB; applying this migration does not copy or upload any existing wardrobe.

## What the migration creates

| Object           | Purpose                                                |
| ---------------- | ------------------------------------------------------ |
| `profiles`       | Optional display name, keyed by the Auth user ID       |
| `clothing_items` | Clothing metadata and the private photo's Storage path |
| `outfits`        | Saved item references belonging to the same owner      |
| `closet-images`  | Private JPEG bucket, maximum 600,000 bytes per image   |
| RLS policies     | Restrict database rows and photo paths to their owner  |

The app will create profiles explicitly if needed; no sign-up trigger is required.
An outfit's `top_category` must match its top (`tops` or `outerwear`). Bottom and
shoe categories are generated by PostgreSQL. Composite foreign keys enforce
ownership and category together. Category edits are blocked while referenced;
deleting a referenced piece deletes dependent outfits. Storage files are separate:
deleting a database row does not delete its photo. The future upload/delete flow
must handle cleanup and failures.

`is_shareable` defaults to false. Setting it true does not grant guest access.
Share links, suggestions, and token validation will come in a separate migration
and server function. No anonymous wardrobe or photo access is granted here.

## Apply it yourself

Use this on the new project created in this chat, before adding wardrobe tables
or a bucket manually. The migration is designed to run once, not repeatedly.

1. In Supabase, confirm you selected your Digital Closet project.
2. Open **SQL Editor** and create a new query.
3. Open `migrations/20261016150129_owner_wardrobe.sql` locally. Copy the entire
   file, including `begin` and `commit`, into the SQL Editor.
4. Review it, then click **Run**. This is the step that creates hosted resources;
   the agent has not executed it against your project.
5. Confirm the editor reports success. If it reports an error, keep the error
   message and do not remove security statements to work around it. The
   transaction keeps the setup from being partially applied.
6. In **Table Editor**, confirm `profiles`, `clothing_items`, and `outfits` exist.
7. In **Storage**, confirm `closet-images` exists and is **private**.

Do not create public-read policies. The dashboard's SQL Editor normally uses a
privileged database role, so being able to read a table there does not verify
that browser users have permission.

## Check the configuration

Run this read-only query in a new SQL Editor query:

```sql
select tablename, rowsecurity
from pg_tables
where schemaname = 'public'
  and tablename in ('profiles', 'clothing_items', 'outfits');

select table_name, grantee, privilege_type
from information_schema.role_table_grants
where table_schema = 'public'
  and table_name in ('profiles', 'clothing_items', 'outfits')
  and grantee in ('anon', 'authenticated', 'PUBLIC')
order by table_name, grantee, privilege_type;

select id, public, file_size_limit, allowed_mime_types
from storage.buckets
where id = 'closet-images';
```

Expected: three tables with `rowsecurity = true`; grants for `authenticated` only
(profiles: SELECT/INSERT/UPDATE; clothing and outfits: also DELETE); one bucket
with `public = false`, size limit `600000`, and MIME type `image/jpeg`.

Grants allow a role to attempt an operation. RLS still decides which rows that
operation may touch. `auth.uid()` is the signed-in user's ID, and each ownership
policy requires it to match the row's owner. An API key alone does not identify
an owner.

Configuration checks are not a substitute for API authorization tests. Once the
app's cloud repository is connected, manually verify owner CRUD, a second user's
isolation, signed-out denial, private photo reads, and upload restrictions.

## Local verification

Run `npm run test:db`. The suite applies the actual migration to embedded
PostgreSQL (PGlite) and executes queries as `anon` and two authenticated users.
It checks owner isolation, write denial, ownership transfers, outfit references,
dependent deletion, and Storage row policies. It does not connect to your project
or require Docker, credentials, or CLI login.

Auth helper functions and Storage metadata tables are minimal local stand-ins.
The hosted Auth/Storage HTTP services, signed URLs, MIME detection, byte limits,
and dashboard event triggers are not exercised. Hosted advisors and actual API
tests remain required before claiming production permissions are verified.
