# Manual database checkpoint

Google sign-in identifies a user. This migration prepares the tables and private
photo bucket that will hold that user's wardrobe. With configuration and a signed-in
session, the React app uses those tables and the private bucket. Applying the
migration does not copy or upload any existing browser wardrobe.

## What the migration creates

| Object           | Purpose                                                |
| ---------------- | ------------------------------------------------------ |
| `profiles`       | Optional display name, keyed by the Auth user ID       |
| `clothing_items` | Clothing metadata and the private photo's Storage path |
| `outfits`        | Saved item references belonging to the same owner      |
| `closet-images`  | Private JPEG bucket, maximum 600,000 bytes per image   |
| RLS policies     | Restrict database rows and photo paths to their owner  |

The app will create profiles explicitly if needed; no sign-up trigger is required.
An outfit's `top_category` must match its top (`tops` or `outerwear`). Bottom and
shoe categories are generated by PostgreSQL. Composite foreign keys enforce
ownership and category together. Category edits are blocked while referenced;
deleting a referenced piece deletes dependent outfits. Storage files are separate:
deleting a database row does not delete its photo. The future upload/delete flow
must handle cleanup and failures.

`is_shareable` is a legacy flag for older selected-piece links. New whole-closet
links do not require individual selection; setting the flag never grants direct guest access.
Share links, suggestions, and token validation are implemented in the separate
[secure-sharing migration and function](SHARING.md). No anonymous table or Storage
access is granted by either migration.

## Apply it yourself

Use this on the new project created in this chat, before adding wardrobe tables
or a bucket manually. The migration is designed to run once, not repeatedly.

1. In Supabase, confirm you selected your Digital Closet project.
2. Open **SQL Editor** and create a new query.
3. Open `migrations/20261016150129_owner_wardrobe.sql` locally. Copy the entire
   file, including `begin` and `commit`, into the SQL Editor.
4. Review it, then click **Run**. This is the step that creates hosted resources;
   the agent has not executed it against your project.
5. Confirm the editor reports success. If it reports an error, keep the error
   message and do not remove security statements to work around it. The
   transaction keeps the setup from being partially applied.
6. In **Table Editor**, confirm `profiles`, `clothing_items`, and `outfits` exist.
7. In **Storage**, confirm `closet-images` exists and is **private**.

Do not create public-read policies. The dashboard's SQL Editor normally uses a
privileged database role, so being able to read a table there does not verify
that browser users have permission.

## Check the configuration

Run this read-only query in a new SQL Editor query:

```sql
select tablename, rowsecurity
from pg_tables
where schemaname = 'public'
  and tablename in ('profiles', 'clothing_items', 'outfits');

select table_name, grantee, privilege_type
from information_schema.role_table_grants
where table_schema = 'public'
  and table_name in ('profiles', 'clothing_items', 'outfits')
  and grantee in ('anon', 'authenticated', 'PUBLIC')
order by table_name, grantee, privilege_type;

select id, public, file_size_limit, allowed_mime_types
from storage.buckets
where id = 'closet-images';
```

Expected: three tables with `rowsecurity = true`; grants for `authenticated` only
(profiles: SELECT/INSERT/UPDATE; clothing and outfits: also DELETE); one bucket
with `public = false`, size limit `600000`, and MIME type `image/jpeg`.

Grants allow a role to attempt an operation. RLS still decides which rows that
operation may touch. `auth.uid()` is the signed-in user's ID, and each ownership
policy requires it to match the row's owner. An API key alone does not identify
an owner.

Configuration checks are not a substitute for API authorization tests. Manually
verify owner CRUD, a second user's
isolation, signed-out denial, private photo reads, and upload restrictions.

## Test the connected app manually

No additional SQL is needed for this checkpoint. Restart `npm run dev`, open
`http://localhost:5173/login`, and sign in with your configured Google test user.

1. A new account should show an empty closet, not the local sample illustrations.
2. Upload one top and one bottom. In Table Editor, confirm two `clothing_items`
   rows have your Auth user ID in `owner_id`. Their `storage_path` values should
   match JPEG files under your user-ID folder in the private `closet-images` bucket.
3. Reload the app. Confirm both pieces and their photos return.
4. In the vertical mixer, choose the pieces and save a named outfit. Confirm an
   `outfits` row stores those exact `top_item_id` and `bottom_item_id` values.
5. Reload, reopen the saved outfit, and verify the selection.
6. Edit a piece's name. Confirm only that row changes. Delete a test outfit and
   confirm the clothing remains. Deleting a piece also removes dependent outfits
   after the application's confirmation.
7. In Settings, sign out; visiting `/closet` should return to login. A second
   Google test user should start with their own empty wardrobe.

For API denial checks, use a browser console or HTTP client with only the public
key and no user session to request the owner tables: wardrobe data must not be
returned. Also verify a second signed-in user cannot read or mutate the first
user's rows or photo folder. Do not use the SQL Editor's privileged role as a
substitute for these checks.

Photo URLs are temporary bearer links; do not paste them into public messages.
The app renews them while in use and offers a refresh button in Settings. Cloud
data is held in memory, not written into the local IndexedDB database. Existing
browser data is preserved; automatic import is not implemented.

Cloud operations require a network connection. Conditional updates/deletes reject
stale records. If a database write response fails, reload before retrying so the
app can read the actual server state. Photos upload before row writes; database
and Storage changes are not one transaction. The app warns if cleanup fails and
can retry known unused-photo cleanup in Settings while that page session remains
open. An uncertain write may leave an unused photo requiring manual review.

## Verification

Use the manual acceptance checks above to verify hosted owner isolation,
wardrobe changes, and private photo access. Automated database tests have been
removed; a successful application build does not verify hosted permissions.
